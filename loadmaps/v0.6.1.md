# v0.6.1 — `/pp-refactor` に、セッションの無い場所の判定基準を与える

## Issue

v0.6.0 が読む順序の 4・5・6 を分けた。

```
4. 設計が決めた理由で、どの文書も持っていない → undocumented-design
5. 設計が決めていないと積極的に言える        → unspecified-choices
6. 4 とも 5 とも判定がつかない理由           → why
```

4 と 5 はどちらも「設計が決めたか」を判定材料に持つ。ADR 0022 はその列を**セッション → リポジトリの
設計文書 → コード**と定めた。第一段をセッションに置いたのは、`/pp` がコードを書いたのと同じ
セッションで走るため、「この値はユーザーが指定したか、自分で決めたか」がその場で分かるからである。

**`/pp-refactor` には掛けるべきセッションが無い。**0022 はこれを既に認めており、「第二段以降からの
推測になる。誤検出は出るが、既存コードの未決着な設計判断を掘り出せることのほうを採る」とした。

v0.6.0 はその取引を成立しなくさせた。残余 `why` があるため、積極的な証拠が揃わない行は推測される
のではなく 6 に落ちる。0022 が受け入れた誤検出は消えるが、掘り出しも消える。既存コードに掛けたとき、
`undocumented-design` と `unspecified-choices` はどちらもほぼ0件になり、`why` だけが太る。

行き先は三つとも periplus なので `/pp-discuss` に並ぶ行は変わらない。落ちるのは分類の解像度だけで
ある。それでも、既存コードのどれだけが未決着の設計判断かを測れなくなることは、v0.5.0 以降
`all.csv`・`swept.csv` を測定の器として扱ってきた方針(ADR 0022 の「掛けた後にログが膨らむことは
受け入れる」)を空振りさせる。

調べた結果、落ちるのは 5 だけではない。4 は「設計が決めた」かつ「どの文書も記録していない」の
二条件を持ち、後半が成立した時点で前半を示せる場所がセッションしか残らない。**4 は
`/pp-refactor` では原理的に発火しない。**

## 決めたこと

- **第一段は scope 段でユーザーが名指しした設計文書。**対象ファイルを聞く場所で一緒に聞く
- **設計文書が決めていないものは実装が決めた。**沈黙が 5 の積極的証拠になる。設計文書が無ければ
  その範囲の理由は全て 5。設計=実装なら実装に倒す
- **4 に残るのは、設計文書が決定を持ち理由を持たない場合。**`/pp-refactor` における
  `undocumented-design` はこの形だけになる
- 0022 の判定材料の列は上書きしない。第一段が抜けたときに第二段が何をするかを決めた

git log は採らなかった。commit の author はこの現場では一人で、「いつ・何が変わったか」は持つが
「設計が決めたか」を持たない。

## 変えたもの

- `skills/pp/SKILL.md` — What counts as settled, for 4 and 5
- `skills/pp-refactor/SKILL.md` — Scope first に設計文書の質問、Classify, then resolve の 4・5 の段
