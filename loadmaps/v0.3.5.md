# v0.3.5 — コードを直す判断を `/pp-resolve` から追い出す

## 概要

`/pp-resolve` は自ら「Where a kind goes is a lookup, not a judgement」と宣言している
(`skills/pp-resolve/SKILL.md:13`)。ところが同じファイルの `:45-61` は、code 行きの全行に
対して「コードに言わせられないか試せ」と命じ、定数抽出・関数抽出・述語命名・アサーション
追加を促す。これは記述の行き先についての判断ではなく、コードの形についての判断である。

**軸が違う。** ADR 0004 が `deliberate-deviation` を判断基準から削ったのと同型の問題で、
軸の違うものを同じ手順に並べれば、行き先の決定にコードの設計の決定が混入する。

破壊性はその症状であって根拠ではない。`/pp` が触るのは自分が今書いたばかりの未コミットの
コードなので、v0.3.1 §3 が `/pp-refactor` で使った「他人のコードだから」という根拠は
そのままでは効かない。効くのは軸のほうである。

## 決定

### 1. try-step を削除する

`skills/pp-resolve/SKILL.md:45-61` の節を丸ごと削る。

ADR 0005 は二つの帰結を持っていた。一つは「コメントを書く前にコードを直せ」、もう一つは
「コードに残る記述は事実の最短の陳述であって、コードの動作の説明ではない」である。**後者は
`:65-67` に残る**ため、0005 が防ごうとした散文化への歯止めは消えない。消えるのはコードを
直せと命じる部分だけである。

定数化・関数抽出・述語命名はいずれも「コードの読みやすさ」の問題であって「コードの外側の
事実」の問題ではない。periplus が保証するのは後者だけである。実際、`API_RATE_LIMIT = 300`
という名前は「その 300 が外部 API のレート制限だ」という事実を半分しか運ばない。

コードを直す判断は、コードを書いている瞬間 — phase 1 — の仕事である。規律としては
ponytail や通常のコーディング規律の管轄であり、記述を濾す瞬間の仕事ではない。

### 2. `unspecified-choices` を十二番目の種別として足す(→ periplus)

try-step が拾っていた記述のうち、捨ててはならないものがある。**設計が決めていない値や形を
実装が裁量で決めたときの、その理由づけ**である。これは設計者と実装者の食い違いから発生し、
未決着の設計判断にあたる。行き先は periplus であり、`/pp-discuss` で方針を決める。

**定義** — 設計が指定していない値や形を、実装が裁量で決めたもの。その理由づけ。

**優先順位** — これで既存の種別と MECE が立つ。

1. 外部の事実が決めているなら `external-facts` → code(外部 API の制限は表の例そのもの)
2. 設計が決めているなら `why` → code
3. **どちらも決めていなければ** `unspecified-choices` → periplus

外部制約に導かれた選択は設計の空白を埋めていない。空白を埋めたのは外部の事実のほうである。
この順で読めば二重該当は起きない。

**判定材料の順序** — セッション → リポジトリの設計文書 → コード。上から順に「これを決めて
いるものがあるか」を見て、どれも決めていなければ弁明にあたる。

第一段をセッションに置くのは、periplus が AI エージェントの現場で動く道具だからである。
設計者はユーザー、実装者はエージェントで、常に二者いる — 「一人プロジェクトなら食い違いは
起きない」という反論はここでは効かない。`/pp` はコードを書いたのと同じセッションで走るので、
「この値はユーザーが指定したか、自分で決めたか」はその場で分かる。設計文書を要さない。

**`/pp-refactor` でも推測で付ける。** 掃除には掛けるべきセッションが無いので、第二段以降 —
設計文書とコード — からの推測になる。誤検出は出るが、既存コードの未決着な設計判断を
掘り出せることのほうを採る。定義は一つのまま、証拠の強さだけが変わる。

**掛けた後に `.log.md` が膨らむのは受け入れる。** 「このコードベースには未決着の設計判断が
これだけある」という正しい信号であって雑音ではなく、減らすために `/pp-discuss` がある。
v0.3.1 §7 が archive を分けたのは `.all.md` が測定の器だからで、`.log.md` は作業キューで
あるため出自が混ざっても困らない。`.swept.md` のような分離はしない。

**`/pp-discuss` は変更しない。** 弁明の主要な道は docs である。`/pp-discuss` で「コードを
直す」と決まったなら、その内容は設計変更であり、決定は docs に吸収される。コードを直すのは
その決定の実行であって、periplus が記録するものではない。五つ目の destination は要らない。

### 3. resolve の引き金規則を `/pp-discuss` の適用範囲に揃える

「出ていく条件を名指していない entry を通すな」という規則は三箇所にあり、同じことを
言っていない。

| 箇所 | いつ効くか |
| --- | --- |
| `skills/pp-discuss/SKILL.md:138-140` | entry を**留める**と決めたときだけ。`here` は構成上引き金を持つ |
| `skills/pp/SKILL.md:185` | 同上の要約 |
| `skills/pp-resolve/SKILL.md:79-82` | **配送の時点**。広すぎる |

広いほうが config の一軸(ADR 0014)を否定している。`external-facts: periplus` に切り替えた
リポジトリでは、ブラウザの癖という事実に対して「これが出ていく条件を書け」と要求される。
事実に出ていく条件は無い。config は「どの種別もどこへでも送れる」と約束しているのに、
下流の規則が「ここに来るのは既定の二種別だけ」を前提にしていた。

同じ2文が「unchanged except for the updated timestamp」と言った直後に「add that condition
now」と言っており、それ自体が矛盾している。これも同時に消える。

`/pp-resolve` の periplus 分岐は「行はそのままログへ。引き金の話は `/pp-discuss` が留めると
決めたときにする」に直す。**ADR にはしない** — 新しい決定ではなく、三箇所の食い違いの是正で
ある。

## 書き起こす ADR

| 番号 | 主題 | 追記先 |
| --- | --- | --- |
| 0021 | コードを直す判断は記述のパイプラインに属さない | `0005` の末尾に、覆された旨(0015 の形) |
| 0022 | `unspecified-choices` — 設計の空白を実装が埋めた選択 | `0014` に一行 |

0022 の中に節として収めるもの — 既存種別との優先順位、判定材料の順序、`/pp-refactor` では
推測になること、掛けた後にログが膨らむのを受け入れること。

**ADR 0014 は上書きしない。** Consequences が「種別を足したい状況は、設定では解決できず、
この ADR を上書きする議論として現れる。それが意図した硬直性である」と予告しており、v0.3.5 は
その経路そのものである。0014 が閉じたのは**利用者が設定で足せないこと**であって、項目数を
永久に十一に固定したわけではない。

ADR にしないもの — 引き金規則の揃え直し(決定 3)。

- `.log.md` の性格づけの変更、`here` の許容、`here`/`docs` の境界 → **v0.3.6**
- 閾値警告と `warnThreshold` の削除 → **v0.3.6**
