# v0.3.1 — 既存コマンドの再構築 `/pp-refactor` の挙動を見直す

## 概要

v0.3.0で、/ppコマンド自体を/pp-classify+/pp-resolveの2コマンドのセットとして扱うように変更した。
そのため、手をつけていない/pp-refactorの挙動が変化する。

v0.3.0 の時点で `/pp-refactor` は次の点で動かない。この版はここから始まる。

| 箇所 | 何が壊れているか |
| --- | --- |
| `:38-40` | `.pre.md` に `- <file>:<line> <comment>` を書く。`ROW_RE` は二重タイムスタンプと `[]` を要求するので一行も数えられない |
| `:14-16` | 「phase 2 is unchanged」— 変わった |
| `:18-20`, `:53` | 「`skills/pp/SKILL.md` の filter を走らせろ」— 単一の filter という手順が消えた |
| 全体 | 種別を一切付けない。`[]` → `[kind]` の機構を丸ごと迂回する |
| `:63-64` | `.pre.md` から消すだけで archive に落とさない |

## 出発点は「破壊」である

`/pp-refactor` の仕事は変わらない — periplus が効いていない環境で書かれたコードから
コメントを抽出し、`/pp` の篩にかけて再配置する。変えるのは抽出の性質である。

現行は **copy** で、ソースを無傷のまま `.pre.md` に写す(`:42-45`)。これが `/pp` との
非対称の原因になっていた。`/pp` は空のソースに書き足すが、refactor は既にあるコメントを
消す・縮める・残すという別の操作をしており、配送が三つの行き先すべてで食い違う。

**cut** にすると、この非対称が消える。

| | `/pp-resolve` | `/pp-refactor`(cut 後) |
| --- | --- | --- |
| code | 無いコメントを書く | 無い。書く |
| periplus | `.log.md` に追記 | `.log.md` に追記 |
| drop | 何もしない | 何もしない |

抽出の時点でソースからコメントが消えているため、その後の状態は「`/pp` の phase 1 を
終えたファイル」と区別がつかない。配送は `/pp-resolve` をそのまま使えばよく、refactor
独自の配送手順は要らなくなる。この版は当初の想定より**小さくなる**。

## 決定

### 1. 抽出は cut にする

`:42-45` が copy を選んだ理由は「実在するコメントがフェーズ間で失われる」だった。cut で
それを引き受けられるのは、ソースが変更済み・未コミットで残るからである。原状は
`git diff` と `git restore` が持つ。

**clean な作業ツリーは要求しない。** Claude Code をはじめ AI ツール自身がバージョン管理
を内部に持つため、規律の側で作業ツリーの状態を検査する必要はない。

代わりに `.pre.md` の重みは増す。`/pp` では失っても「書かれなかったノート」が消えるだけ
だが、cut 後は実在したコメントが消える。`:80-82` の境界は弱まるのではなく強くなる。

### 2. 抽出時にも規則(i) で分割する

逐語で抽出して `/pp-classify` に割らせる案は採らない。v0.3.0 で `.pre.md` を原子的に
した意味が失われる。

逐語性を守る根拠として `:80-82`(「`.pre.md` は removed の記録」)を挙げたが、これは弱い。
収集中ソースは無傷であり、書き戻した後は `git diff` が何を消したかを正確に持ち、割った
行は同じ `file:line` と同じ作成日時を持つので兄弟であることは行から読める。逐語である
必要までは要求されていない。

規則(i) は粒度の規則であって分類の判断ではないため、`:47-49`(収集中に選り分けるな)とも
矛盾しない。取りこぼしは `/pp-classify` の再帰分割が拾う — 捕獲と同じ二段構えになる。

その代償として、`.pre.md` から元の一文を厳密に組み立て直すことはできなくなる。接続詞が
落ちるためである。原状復帰はハーネス任せになり、規律の側では書けない。

### 3. 配送は `/pp-resolve` に委譲する。例外は一つだけ

`/pp-resolve` の code 分岐は、コメントを書く前に「コードに言わせられないか試せ」と命じる。
`/pp` ではコードが未固定で有効だが、掃除では他人が書いた既存コードに当たる。現行 `:82-84`
はこれを明示的に禁じている。

**掃除ではこの手順を走らせない。** 見つけた場合は報告に一行出すだけにする。コード本体に
触ったらリファクタリングではなくなる。

分岐は `/pp-refactor` 側に一文置くだけで、`/pp-resolve` の本文は変えない。掃除をしない
リポジトリが読む文章は増えない。

### 4. ファイル1つずつ完結させる

```
cut → classify → resolve → 次のファイル
```

範囲全体を先に刈る案は採らない。理由は二つある。合意の前に範囲全体が刈られること、
そして行番号が全部ずれること — 範囲全体を先に刈れば `.pre.md` の `file:line` は刈る前の
座標を指したまま、ソースは別の座標系になる。

copy だった頃はこの粒度に反対する理由があった。「20ファイル中3ファイルで中断したとき、
残りを指すものが無くなる」である。cut ではソースが刈られたまま残るため、`git status` が
中断を告げる。放棄の可視性はむしろ上がる。

### 5. ファイル単位の合意は廃止する

`:58-73` の段落群(差分を見せて聞く・一ファイル一合意・バッチは異議を素通しさせる)を削る。
`/pp-refactor` は対話を持たない一括処理になり、最後に報告する。

cut によって「破壊の前」という合意の位置が失われたことから出た決定である。

### 6. コメントの書き直しを許す

`:54-56`(既に正しい形なら触らない)と `:75-76`(全部そのまま残るのは正常な結果)を削る。
掃除を走らせたファイルのコメントは、生き残ったものも含めて書き直された形で戻る。

コメントのリファクタリングなのだから、書き直すのが仕事である。

なお**翻訳は別の規則**であり、`skills/pp/SKILL.md` の「捕獲した言語のまま運べ」は掃除にも
効いたままである。

ただし現状、その規則は書く場所に届いていない。`/pp-resolve` の code 分岐にあるのは
「Keep the language the row is in.」の一節だけで、`skills/pp/SKILL.md` が持つ後半 —
周囲のコードと言語が食い違う場合はそれを報告すべき不一致として扱い、黙って訳さない —
が落ちている。そして `/pp-resolve` は通常経路で `skills/pp/SKILL.md` を読まない。

v0.3.0 の実装中に実際にこれを踏んだ。日本語で捕獲した行が英語で書き戻され、不一致は
報告されなかった。規律を無視したのではなく、規律が届いていなかった。**`/pp-resolve` の
code 分岐に規則の全体を明示する。**

### 7. 掃除の archive は `.periplus/.swept.md` に分ける

ADR 0015 は「`.pre.md` に入った行は全て `.all.md` を通る」と決め、掃除の分もそこに入ると
書いた。cut にしたことでこれが持たなくなる。掃除は既存コメントを全部刈るので、コメントが
500 個あるコードベースで一度走らせれば `.all.md` は他人が書いた 500 行に埋まる。

より重い問題として、**periplus を通したコードを後から掃除した場合**、刈られたコメントが
`.all.md` に入れば、それが `/pp` の配送したものなのか新しく捕獲したものなのか区別が
つかなくなる。`/pp` が機能不全を起こしているかどうかを、そのファイルからは判断できない。

分けておけば逆に診断になる。`/pp` が code に配送したコメントが後の掃除で `tautology` と
判定されたなら、それはフィルタが素通しした証拠として読める。

副次的に、`.swept.md` は**対照群**になる。規律の下で書かれたコメント(`.all.md`)と、規律の
無い場所で書かれたコメント(`.swept.md`)を並べれば、tautology と history の比率が実際に
違うのかを比較できる。

不変条件は「`.pre.md` を出た行は必ず archive に着く」と書き直す。archive が二つあり、
どちらに着くかは行の出自で決まる — 三ファイルで採った「どのファイルに居るかが状態を言う」
と同じ考え方である。書式は同型のままなので、`ROW_RE` も読み書きの手順も変わらない。

### 8. `/pp-refactor` は独立した skill のまま残す

中身は薄くなる(範囲確認と、ファイルごとの `cut → /pp`)。それでも独立させるのは、発火の
トリガーが違い、既存コードを破壊するという危険も違うためである。

## 書き起こす ADR

| 番号 | 主題 |
| --- | --- |
| 0017 | `/pp-refactor` は既存コメントを copy せず cut する |
| 0018 | 掃除の archive を `.swept.md` に分ける(ADR 0015 の修正) |

0017 の中に節として収めるもの — 合意を持たない一括処理にすること(`:70-73` は「バッチは
異議を素通しさせる」と書き `/pp-discussion` の評価まで引いているので、覆す記録が要る)、
コメントの書き直しを許すこと、抽出も分割の対象であること(ADR 0013 が縛るのは捕獲だけか
という論点への回答)。

ADR にしないもの — コード本体に触らないこと(`:82-84` の維持であって新しい決定ではない)、
dirty な作業ツリーを要求しないこと(何もしないという決定なので書くものが無い)。
