# v0.3.3 — ログの行き先を四つにし、`/pp-discussion` を改名する

## 概要

二つを一つの版で出す。出口の再定義が本体で、改名はそれに合わせる。

仕事が変わるなら名前は仕事が決まってから付ける。改名を先に切ると、直後に中身が変わって
名前を選び直すことになる。

## 1. 四つの行き先

```
code  → コードにコメントとして書く（分割漏れの救済）
docs  → そのリポジトリが既に持っている文書に足す
here  → 文書に属するが、収める文書がまだ無い。ログに留まる
trash → どこにも残さず捨てる
```

`.log.md` に既定で入る種別は `rejected-alternatives` と `upgrade-triggers` の二つだけで、
どちらも文書の材料である。ログは元々「文書行きの控室」だった。昇格先を ADR に限っていた
ことは、この性質を半分しか認めていなかった。

`docs` の行き先はリポジトリごとに違い、既定は無い。`/pp-discussion` は最初のエントリを
取り上げる前に一度 repo の文書構成を見て、文書を名指しで提案する。config には置かない。

`here` は出口ではなく `docs` の保留形で、引き金を構造上必ず持つ（その文書ができたとき）。
文書を持たないリポジトリでは全件が該当しうるため、歯止めは反復に置く — 同じ主題が二度目に
`here` へ落ちたとき、それが文書を作る根拠になる。

`docs` の通過試験は行き先の文書が持つ。ADR なら三条件、ロードマップなら着手する意思、
用語集なら横断的に使われる語。どの試験にも通らないものは `trash`。

`/pp-resolve` の kind→行き先の表は変えない。`docs` は合意を要するので機械側に置けず、
`periplus`→`here` の改名は利用者の `config.json` を壊す。

→ `docs/adr/0020`

## 2. 改名

コマンド名は動詞で名乗る、という原則を既存のコマンドに適用する。`discussion` だけが
名詞であり、`pp`・`classify`・`resolve`・`refactor` は動詞である。

名詞の名前は、それが状態を指すのか操作を指すのかを読み手に決めさせる。`/pp-resolve` が
「解決する」と読めるのに対し、`/pp-discussion` は「議論」という物を指しているように読め、
何が起きるのかが名前から確定しない。

原則そのものは `CONTEXT.md` の「コマンド名」に置いてある。

利用者が打つコマンド名の破壊的変更であるため、旧名は残さない。Claude Code のスキルに
alias 機構は無く、残すにはディレクトリを丸ごと重複させるしかない。

## 名前の決定

`/pp-discuss` を採った。元の問題は `discussion` が名詞であることであり、`discuss` は
動詞形で原則を満たす。加えて、一件ずつ合意を取る性質が名前に残る — このコマンドの
Boundaries 節は丸ごと「まとめて処理しない」ことの説明であり、そこが消える名前は避けた。

却下した候補:

- `drain` — 効果を名乗り、`classify`・`resolve` と最も揃う。ただし `here` があるので
  全件は drain されないし、一括操作を連想させる。それはこのコマンドが最も強く禁じている
  振る舞いである
- `route` — 新しい仕事をそのまま名乗る。`resolve` と意味が近く、ADR 0016 で機械側に
  置いた `/pp-resolve` との線がぼやける

`discuss` が**過程**を名乗る動詞であり、`classify`・`resolve` が**結果**を名乗るのと
揃わない点は残る。効果（ログが減る）は名前から出てこない。この不揃いは承知の上で採った。
