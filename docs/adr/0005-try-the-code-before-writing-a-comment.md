# コメントを書く前に、コードに言わせられないかを試す

判断基準は「その記述をどこへ送るか」を決めるが、「そもそも記述が要るか」は問わない。
そのため ADR-0004 で「今のコードについて真であること → code」と定めたところ、それが
コードを散文で解説する許可として読まれ、マジックナンバーの弁明と条件式の言い換えで
3行のコメントが生まれた。避けたかったコードのドキュメント化そのものにあたる。

そこで分類の手前に一段を置く。コメントを書きたくなったら、まずコードにそれを言わせ
られないかを試し、記述が消えるかどうかを見る。名前のない数値は定数名を欲しており、
見出しを欲しがるブロックは関数への抽出を欲しており、説明を欲しがる条件式は述語名を、
明示したい不変条件はアサーションかテストを欲していることが多い。これを通過したものだけ
が判断基準の表に到達する。

`block-headings` の行に既にこの考え方は入っていたが、一項目の特殊規則に閉じ込めていた。
一般化すべきものだった。

## Consequences

規律が「書く場所を変えろ」だけでなく「コードを直せ」と要求するようになり、実行が重く
なる。評価でもスキルあり側は一貫して遅くトークンも多い。この一段はその傾向をさらに
強める。

コードに残る記述には形の制約も加わった — 事実を最短で述べるものであって、コードの動作の
説明ではない。読み手にはコードが見えており、見えないのはコードの外側だけである。

**この ADR の前半は ADR 0021 で覆された。** 「コメントを書く前にコードに言わせられないかを
試す」一段は `/pp-resolve` から削除された。行き先を lookup で決める手順の中に、コードの形に
ついての judgement が一つ残っていたためである。上の段落の**形の制約は生きている** — 0005 が
決めた二つのうち、消えたのは「コードを直せ」のほうだけで、「事実を最短で述べよ」は残る。

この一段が拾っていた記述のうち、設計が決めていない値や形を実装が裁量で決めたときの理由づけ
は、ADR 0022 が `unspecified-choices` として種別で拾う。
