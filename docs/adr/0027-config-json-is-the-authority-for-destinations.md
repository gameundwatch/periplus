# `config.json` が行き先の唯一の権威であり、無ければ作られる

行き先の記述は三箇所にある。`skills/pp/SKILL.md` の criteria-table の三列目、
`hooks/periplus-activate.js` の `DEFAULT_CRITERIA`、`README.md` の四列表である。このうち
**SKILL.md の列は既に死んでいる。**hook が注入時に JS の値で置換しており、十二種別は両方に
揃っているので、出荷された列へのフォールバックは到達しない。

```js
return m ? `| \`${m[1]}\` |${m[2]}| **${criteria[m[1]] || m[3]}** |` : line;
                                          ↑ JS が勝つ    ↑ 到達しない
```

権威の所在を実態に合わせる。**SKILL 本文から行き先の記述を撤去し、`.periplus/config.json` を
唯一の権威とする。**

ADR 0014 は「行き先は JS に書き直さず、出荷された表の欄だけを差し替える — 種別の文言の住所を
一つに保つため」と決めた。文言の住所が一つであることは動かない。動くのは、行き先が種別の文言と
同じ表に載っている必要は無かった、という点だけである。

## 種別の説明から行き先が消える

`/pp-classify` は既にこう命じられている。

> **Ignore the destination column** — where a kind goes is `/pp-resolve`'s business, and
> knowing that `history` is dropped is exactly the pressure that makes a note get called
> something else so that it survives

ところが `skills/pp/SKILL.md` の種別の説明そのものが、行き先を根拠に判別を語っていた。
`current-limits` と `upgrade-triggers` の対は「限界はコードの傍に、持ち上げる意図はログに」で
区別され、`unspecified-choices` の読み順は「決着させるのは設計であり、だからログに行く」で
締められている。**`why: drop` や `unspecified-choices: code` のような設定では、この根拠がその
まま嘘になる。**行き先が設定で動くことは ADR 0013 が既に指摘し(「行き先は設定で変えられるため、
どのような割れ方も正当でありうる」)、ADR 0014 は行き先の解決を機械の仕事と定めている。文面だけ
がそれに従っていなかった。

**判別は「その note が何であるか」だけで語る。**`current-limits` と `upgrade-triggers` は
「いま真であること」と「後でやること」で分ける — ADR 0004 が引いた分割線がそのまま使える。
`why` と `unspecified-choices` の読み順は残し、区別は `/pp-discuss` での扱い(why は設計の記述
材料、unspecified-choices は設計の穴)で説明する。

これは新しい決定ではなく、三箇所の食い違いの是正である。独立した ADR にしないのは、是正すべき
根拠がこの決定にしか無いためである。

## 無ければ作り、中身は上書きしない

行き先の権威が `config.json` にあるということは、**それが常に存在しなければならない**という
ことである。セッション開始ごとに存在を見て、無ければ十二種別すべてを書いた既定で作る。中身は
一切上書きしない。

**ADR 0010 を覆す。**0010 は明示的にこう決めていた。

> `config.json` は hook では書き出さない。既定値をファイルとして固定すると、プラグイン側の
> 既定が更新されたときにリポジトリが古いスナップショットを持ち続けることになる。設定を置いて
> いないリポジトリは常に出荷時の既定に追随する。

追随は失われる。既定を動かす版(ADR 0026 がまさにそれである)を出しても、既存のリポジトリの
`config.json` は古い行き先を持ち続ける。それでも引き受けるのは、権威が一箇所であることのほうが
重いからである。二箇所の権威が黙って食い違うより、一箇所が古いほうが直せる。

**`.periplus/` の生成に相乗りさせてはならない。**ディレクトリが既にあれば即座に返る関数であり、
それは 0010 が決めた「書き込みは初回のみ」の形である。同じ判定に足すと、既に periplus を使って
いる利用者全員に `config.json` が永久に作られない。ディレクトリと `config.json` は別々に存在を
見る。

`.gitignore` の追記とは振る舞いが違うことになるが、線は引ける。ignore 行は他人のファイルへの
追記であり、`config.json` は periplus 自身のワークスペースにある自分のファイルである。**規律が
自分の設定ファイルを持つことと、他人のファイルを書き換えないことは別の話である。**

読み取り専用の問い合わせでは作らない。問い合わせが `.periplus/` を生やさない現行の設計を維持
する。

## 追跡しない。作成も報告しない

`.periplus/` は全体が gitignore される(ADR 0009)。`config.json` が権威になっても、この線は
動かさない。`.gitignore` にも触らない。

新しいクローンには既定の `config.json` が生成され、チームが意図して書いた設定と見分けがつかなく
なる。**これは運用するチームの問題であり、規律が引き受ける責務ではない。**生成したことを起動時の
ヘッダで報告する案も採らない。利用者の運用に対する通知は、規律の仕事ではない。

## README は行き先を残す

`README.md` の四列表は行き先の列を持つ。**この決定の唯一の例外として残す。**model が読んで分類に
使う文書ではなく、導入前の人間が読む紹介であり、既定が何であるかは紹介に要る。
`DEFAULT_CRITERIA` と二重になるが、ズレても分類は壊れない。

## Considered Options

- **`.periplus/` の生成に足す** — 差分は最小。既存の利用者全員に永久に作られない。
- **`config.json` を追跡対象にする** — チームの線がレビュー可能になり、生成物と意図した設定の
  区別もつく。ADR 0009 を覆すことになり、`.periplus/` の意味が「作業状態を置く場所」から変わる。
- **SKILL.md の表をフォールバックとして残す** — node が動かないときの保険になる。`config.json`
  が常に在って十二種別を完備するなら JSON を直接読むほうが確実で、死んだ列を生かしておく理由も
  消える。
- **生成をヘッダで報告する** — 生成物と意図した設定の区別が利用者につく。一度きりの出来事の
  ために、毎セッションの一行を払う。

## Consequences

`DEFAULT_CRITERIA` は JS に残る。生成に要り、手で壊された設定の穴埋めにも要る。**権威は
`config.json` だが、その中身の出所は依然として JS である。**行き先の記述が二箇所から一箇所に
なったのではなく、片方が生成物になった。

`/pp-resolve` のフォールバックは SKILL.md の表を読むのをやめ、`config.json` を直接読む。解決に
失敗したことを報告する経路(ADR 0014)は、読む対象が変わるだけで残る。

プラグインの既定が更新されても、既存のリポジトリは追随しない。ADR 0010 が予告した代償を、ここで
払っている。既定を動かす版は、利用者が手元の `config.json` を消すまで届かない。
