# 分類は一本の木が行い、表は名前と内容だけを持つ

ADR 0029 は「表は 4・5・6 を分けられない。分けるのは順序であり、順序は表の下、一箇所に置く」と
決めた。v0.7.5 は表の 2 列目からその判別の文言を落とし、決定の半分を実装した。

**残りの半分が実装されていない。**順序が触るのは 13 種のうち 8 つで、`block-headings`
`rejected-alternatives` `upgrade-triggers` `history` `test-intent` は表の定義でしか決まらない。
1 行に分類器が二つ当たり、どちらを先に読むかはどこにも書かれていない。

「以前は同期だった」が ADR に書かれていれば、順序は段 3 で `doc-restatement` と答え、表は
`history` と答える。この衝突は 0029 が縮めた側にも出る。ADR 0026:47 が `block-headings` と
`tautology` について同じことを既に書いており、他の四つは記録されていない。

## 記述の形を三問で決め、判定を枝に置く

```
ルールか → 他所から読めるか → 理由か
```

三問が形を決め、その中の判定は枝ごとに違う。1 行が通る問いは最大 4 つで、途中で表に戻らない。
木は `skills/pp-classify/SKILL.md` に mermaid で置く。

**分岐を散文で書くと表と二重になる。**v0.7.5 までの経緯がその実測である。0029 が「一箇所に置く」
と書いた散文の節は、表の 2 列目と同じことを述べ、しかも五つの種別を取りこぼしていた。図であれば、
入口の無い種別は描けないことで露出する。ADR 0012 が禁じたのは機械的な強制であって、仕様を図で
書くことではない。

**「ルールか」は「他所から読めるか」より前にある。**これが 0029:95 の「1 は 3 より前」を引き継ぐ。
文書化済みの外部事実が `doc-restatement` に吸われれば、0026 が数えた地雷 8 件がコードから消え、
ADR 0004 が防いだ「次の読み手が善意で壊す」が戻る。0029 はこれを但し書きで支えていた。木では枝の
分かれ方が支える。

## `contracts` は主題で定義し直す

「シグネチャと型が**表現していない**義務」は残余の形をした定義で、型注釈のある言語では空になる。
実測でも実コード 0 件だった。ADR 0029:21 が `doc-references` に当てた検査 —— 主題ではなく文の形を
名乗る種別は発火しない —— に同じく掛かる。

**「実装者が決めた制約か」**で分ける。決めたのが自分以外なら `external-facts`、実装者なら
`contracts`。0029 が理由を「誰が決めたか」で割った軸を、事実側に伸ばしたものである。
`unspecified-choices` の「実装者の裁量」(ADR 0022)と同じ言葉を使う。

この定義では、同じリポジトリの別ファイルとの取り決め —— 「SKILL.md の表は 2 列」「テストが
SKILL.md と `DEFAULT_CRITERIA` の一致を保証している」—— が `contracts` に入る。いま
`external-facts` に着いている行の一部が動く。

## `history` を落とし、`default` を足す

`history` に固有の領域が無い。文書化された変更は「他所から読めるか」が拾って `doc-restatement`
になり、文書化されていない変更は「設計が決め、記録が無いか」に吸われる。ADR を書くリポジトリでは、
記録に値する変更はまず ADR になる。自リポジトリの `history` は 4 行あり、4 行とも ADR に行まで
名指しできた(0026:28-29 / 0026:40 / 0027:3-6 / 0027:104)。

**`default` は残余の残余である。**0029 は `why` を「判定できなかったことを判定できなかったまま
記録する場所」として残余にしたが、`why` の条件は「理由であること」であり、理由の形をしていない行
は受けない。`history` がその位置を塞いでいたので、落とすと穴が開く。`default` はその置き場で、
既定は `periplus` —— 決着していないものはログに溜まる、という 0026 の既定と同じ扱いである。

種別は 13 のまま。集合を動かすので ADR 0014 に当たるが、0014 が閉じたのは利用者が設定で足せない
ことであって項目数ではない。

## 表は README にだけ置く

木が分類するなら、`skills/pp-classify/SKILL.md` に表を置く理由が無い。ADR 0032 が表をそこに置いた
のは「分類器の道具だから」であり、その前提はこの版で消えた。**両方あると、同じ行に二つの記述が
並ぶ。**v0.7.5 が消したのは同じ判別が二度書かれていることで、内容の表と判定の木が同じファイルに
同居する形は残っていた。

hook が読む先を `README.md` に変える。README の表は kind・内容・例・既定の行き先を持ち、
`/pp-resolve` が印字するときは最後の列だけがこのリポジトリの設定で置き換わる。**列を足すのでは
なく置き換える** —— 出荷時の既定と解決後の行き先が並ぶと、古いほうがどちらか分からない。

分類器が持つのは木だけになり、種別の名前は木の葉として現れる。「どの種別も木のどこかの葉である」
ことはテストで固定した。表が名前を数える役から降りたので、数を保証する場所も木に移る。

`/pp-classify` の本文は 8,155 字から 6,732 字になる。

## `block-headings` を `label` に改名する

木の第一問は「文か、ラベルか」で、そこで取れるのは**ラベルであるという事実だけ**である。見出しか
どうかはその先の話で、名前が事実より狭い。0029 が `doc-references` を改名したのと同じ —— 名前が
実際に取れるものとずれている。行き先は `code` のまま動かさない。

## Considered Options

- **順序の一段目の文言だけ直す**(当初案) — 「消えると壊せる」は `current-limits` の実測に当たら
  ない。だが直しても表と順序の二重は残り、入口の無い五つも残る。
- **`contracts` を `external-facts` に吸収する** — 実測 0 件が根拠だった。「実装者が決めたか」で
  主題として分けられるので、廃止の理由は名前ではなく定義の形にあったことになる。
- **`rejected-alternatives` を `unspecified-choices` に吸収する** — 「その案を実装したか」の二択で
  分かれるので、統合する必要が無い。`/pp-discuss` は ADR の試験に「退けた選択肢を記録する」を
  置いており、印が消えると `## Considered Options` の素材が分からなくなる。
- **分岐を復元元の一本にする** — 木の第二問がその軸だが、骨まで置き換えるのは 0029 の順序その
  ものに当たる。`loadmaps/unassigned.md` に残す。
- **何もしない** — 表が分類器のまま残る。0029 が「この設計で最も脆い一点」と呼んだ場所である。

## Consequences

既存の `config.json` に `history` や `block-headings` を書いている利用者には `unknown kind` が
出て、そのキーだけが落ちる。`label` と `default` は install が既定値で追記する。0029:132-144 が
改名のために用意した経路が、そのまま両方に働く。

**`default` が増えたら、三問が粗いという信号である。**残余は判定できなかったことの記録であって、
分類の逃げ場ではない。次の `swept.csv` で最初に見るのはこの件数である。

`label` と `test-intent` は分岐が付いた。発火するかどうかは、これも次の `swept.csv` を見る。
0 件が続いても、母集団に対象が無ければ種別の性能とは関係が無い —— 自リポジトリのコーパスには
テストファイルが一つも入っていない。
