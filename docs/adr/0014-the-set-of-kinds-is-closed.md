# 種別の集合は閉じる。設定できるのは行き先だけで、その解決は機械が行う

ADR 0002 は判断基準を列挙し、設定ファイルで個別に切り替えられるようにした。この版で
その機構に三つの修正を入れる。

## 語を二つに分ける

`criteria` が一語で二つの仕事をしていた。設定ファイルが持っている対応表と、pre-comment
一件に貼るラベルである。前者は規則で、後者は分類であり、別物である。

- **判断基準 / criterion** — 種別を行き先に対応づける規則。`config.json` が持つのはこれ
- **種別 / kind** — pre-comment 一件が持つ、ちょうど一つの分類

`tag` は採らない。複数付く前提の語であり、ADR 0013 の「一件一種別」と衝突する。
設定ファイルのキーは `criteria` のまま据え置く。あの JSON が持っているのは実際に規則表
だからであり、改名すれば既存の設定が警告なく無効化される。

## 種別の集合は閉じる

利用者が独自の種別を追加することはできない。切り替えられるのは行き先だけである。

種別が MECE であることは、項目が互いを排除するよう選ばれていることで成立している。
定義文付きの項目が一つ増えたとき、その MECE を検証する者は誰もいない。項目を足したく
なる状況とは、既存のどれにも当てはまらない新しいカテゴリが要るということであり、それは
設定ではなく規律の変更にあたる。

未知のキーと不正な行き先は警告する。これまでは黙って捨てられており、設定したつもりの
利用者を既定値のまま走らせていた。設定を無効化することと、無効化したと知らせないことは
別の話である。

## 名前はコードの属性ではなく記述の主題を指す

`history` を `legacy` に改名する案を却下した。`legacy` は「まだ現役だが古いコード」という
コードの属性を指す語であり、種別が分類しているのは記述の主題である。改名すると二方向で
誤仕分けが起きる。

- 「以前は同期だった」は経緯だが、そのコードは最新版であって legacy ではない
- 「この分岐は v1 クライアント(legacy)のために残してある」は `current-limits` で
  **コードに残すべき**記述だが、名前の一致で `legacy` に吸われ破棄される

後者が実害である。ADR 0004 が防ごうとした「次の読み手が善意で削除する」状況が、名前の
選択だけで戻る。

## 設定が効く経路を機械化する

これまで設定が効く経路は「phase 2 で config を読め」という一行の指示だけで、読んだか
どうかを検証する手立てが無かった。`buildContext` は `criteria` を引数に取りながら本文で
使っておらず、README は hook が criteria を差し込んで注入すると書いていたが、そうは
なっていなかった。

`/pp-resolve` は表を読むのではなく、解決済みの表を受け取る。行き先は JS に書き直さず、
出荷された表の欄だけを差し替える — 種別の文言の住所を一つに保つためである。

解決に失敗した場合は既定表にフォールバックし、そのことを報告する。規律が止まるよりは
設定を無視してでも濾すほうがよいが、無視されたことに気づけない利用者を作ってはならない。

`/pp-classify` はこの表を使わない。種別の定義だけを読み、行き先は見ない。`history` が
破棄されると知っていることは、破棄されないよう別の名前を選ばせる圧力になる。

## Considered Options

- **種別を開き、定義文付きで追加できるようにする** — 「一般化」としては筋が通る。ただし
  行き先だけでは足りず定義文が必須になり、設定ファイルが規律の一部を持つ。追加された
  項目が既存と MECE かを検証する手立ては事実上無い。
- **設定キーを `to` に改名する** — `to.why = "code"` のほうが意味は読みやすい。ただし
  既存の `config.json` が警告なく無効化され、いま直そうとしている沈黙の故障を新たに
  一つ作る。読みやすさの差は破壊的変更を正当化しない。

## Consequences

規律の緩め方は「行き先を動かす」一種類だけになった。種別を足したい状況は、設定では
解決できず、この ADR を上書きする議論として現れる。それが意図した硬直性である。
