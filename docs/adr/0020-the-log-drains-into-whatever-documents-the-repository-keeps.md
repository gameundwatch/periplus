# ログの主経路を「そのリポジトリが持っている文書」に開き、行き先が無い場合は留まることを行き先の一つにする

ログの出口は pick(コード)・昇格(ADR)・破棄 の三つだった。これを四つの行き先に置き換える。

```
code  → コードにコメントとして書く
docs  → そのリポジトリが既に持っている文書に足す
here  → 文書に属するが、収める文書がまだ無い。ログに留まる
trash → どこにも残さず捨てる
```

## なぜ ADR 限定をやめるか

`.log.md` に入る種別は既定で `rejected-alternatives` と `upgrade-triggers` の二つだけで
ある。どちらもコードが依存する事実ではなく、文書の材料にあたる。つまりログは元々
「文書行きの控室」だった。昇格先を ADR に限っていたことは、この性質を半分しか認めて
いなかった。

ADR の三条件に通らない設計上の記述は、実際には破棄か据え置きしか選べなかった。
`upgrade-triggers` が典型で、「いつか直す」はロードマップの材料であって ADR ではない。
行き先が無いために捨てられていた。

## 行き先はリポジトリごとに違う

このリポジトリが ADR とロードマップを持っているのは、これを書いた者がそう作ったから
であって、一般的な形ではない。設計文書を全く持たないリポジトリも、README の一節だけを
持つリポジトリも現実にある。

したがって `docs` は特定のファイル構成を指さない。**そのリポジトリが実際に持っている
文書**を指す。`/pp-discuss` は最初のエントリを取り上げる前に一度だけ repo を見て、
何が置かれているかを把握してから、文書を名指しで提案する。

設定ファイルには置かない。行き先の文書を config に書かせると、設定した時点の構成が
固定され、文書が増えても追随しない。加えて ADR 0012 の「散文で聞き、機械的に強制しない」
に反する。`/pp-discuss` は元々一件ずつ合意を取る対話であり、行き先の文書もその中で
決まれば足りる。

## `here` を行き先の一つにする

ADR 0003 は「置かれた記述は pick・昇格・破棄 のいずれかで**必ず出ていく**」と定義した。
`here` はこの文言を変える。趣旨は変えない。

据え置きは以前から起きていた(`/pp-discuss` の「Entries that stay」)。名前が無いまま
起きている状態が最も腐るため、名付ける。名付けた上で、0003 が本当に禁じていたもの
——出ていく条件を持たない永久在庫——は禁じたままにする。

`here` は引き金を構造上必ず持つ。出ていく条件は「それを収める文書ができたとき」であり、
選んだ時点で条件が決まっている。0003 の Consequences（出口の無いエントリは永久在庫）は
そのまま生きる。

## `here` が既定になる危険と、その歯止め

「収める文書が無い」は、設計文書を持たないリポジトリでは全件に当てはまる。そのままだと
フォールバックが既定になり、ログが store に戻る。0003 が避けたかったものそのものである。

歯止めは反復に置いた。**同じ主題の記述が二度目に `here` に落ちたとき、それが文書を作る
根拠になる**。記述一件のために文書体系を新設することはしないが、一つの主題に二件溜まる
ことは、その文書が要るという証拠として十分である。

これは新しい仕掛けではない。`/pp-discuss` は既に「同じノートが繰り返し戻ってくるなら、
まだ書かれていない ADR だ」と言っており、その規則を `here` の再訪条件として引き取った
だけである。

## `/pp-resolve` の表は変えない

行き先の語彙は `code`/`docs`/`here`/`trash` になったが、`/pp-resolve` が引く kind→行き先
の表は `code`/`periplus`/`drop` のままにする。

`docs` をそこに置けないためである。文書を書くことは合意を要する作業であり、ADR 0016 で
`/pp-resolve` に割り当てたのは機械側の仕事だった。種別から機械的に ADR が生成される経路は
作らない。

`periplus`→`here`、`drop`→`trash` の改名も見送る。利用者の `.periplus/config.json` が
持っている値を壊す(ADR 0002)。同じ行為に二つの名前が残るが、揃えるために設定を壊すより
安い。**二つの表が別の語彙を持つ理由は、この節が根拠である。**

## Considered Options

- **ADR 限定のまま据え置く** — 通過試験(覆しにくい・驚く・トレードオフ)が強く、昇格が
  稀に保たれる。ただし ADR に通らない設計上の記述の行き先が無いままになる。
- **`docs` を一つの置き場に固定する**(`docs/notes.md` など) — 行き先が決まっているので
  提案が簡単になる。リポジトリの既存の文書構成を無視して新しい置き場を増やすことになり、
  実際には誰も読まないファイルが一つ増える。
- **行き先の文書を config に書かせる** — 提案が確実になる。構成の変化に追随せず、
  設定していないリポジトリでは何も起きない。
- **`here` を名付けない** — 0003 の文言をそのまま保てる。据え置きは起き続けるので、
  名前の無い状態が残る。

## Consequences

`docs` の通過試験は一つではなくなり、行き先の文書が持つ。ADR なら三条件、ロードマップ
なら着手する意思、用語集なら横断的に使われる語。**どの文書の試験にも通らないものは
`docs` ではなく `trash` である。** 行き先を広げたことは、通る記述を広げる根拠にならない。

`/pp-discuss` は開始時に repo の文書構成を一度見る手順を持つ。エントリごとに探すのでは
なく、最初に一度である。これが無いと「どの文書に入れますか」と白紙で聞くことになり、
提案する対話ではなくなる。

報告の形が変わる。`<N> picked, <M> promoted, <K> discarded, <R> remaining` は
`<N> to code, <M> to docs, <K> trashed, <R> held here` になる。
