# v0.6.0 — `why` を三つに割り、`doc-references` を修復する

## 概要

`why` を periplus 送りにしたところ(ADR 0026)、`/pp-discuss` で「文書から容易に復元できるため
trash」という判断が急増した。この版はその急増を扱う。

**濾過は故障していない。**`/pp-discuss` は正しく判定している。落ちているのは出力の質ではなく、
機械的に引ける判定に合意の対話を使っているという配分である。`/pp-discuss` は一件ずつユーザーの
合意を取る場であり(ADR 0012)、「ADR 0028 に書いてある」は合意を要する判断ではなく事実確認である。

自リポジトリの実測(`all.csv` 18行 + `swept.csv` 50行 = 68行)。

| kind | 件数 | 何が起きているか |
| --- | --- | --- |
| `why` | 24 | 性質の違う三つを一つで抱えている |
| `doc-references` | 1 | 定義が「ポインタ」という**形**なので、内容の重複を弾いている |
| `unspecified-choices` | 0 | 隣の `why` が先に吸っている |

`doc-references` の唯一の1件は、定義どおりのポインタではない。

```
.periplus/all.csv:16  hooks/periplus-activate.js:127  doc-references  "種別の集合は閉じている"
```

これは ADR 0014 が持っている**内容**であって、文書への参照ではない。表の定義と、実際に分類器が
撃っているものが既に食い違っている。

**原因は名前の軸である。**ADR 0026 は drop の四つをこう並べた。

```
drop : tautology, doc-references, history, test-intent  ← 他所から復元できる
```

`tautology` はコードから、`history` は git log から、`test-intent` は describe/it から復元できる。
四つは**復元元**で組織されている。`doc-references` だけが復元元ではなく形で定義されており、その
一つだけが発火していない。

`why` は逆向きの同じ誤りである。**文の形(理由であること)を名乗っているので吸いすぎる。**
ADR 0026 のコーパスでは 44/108、`swept.csv` では 21/50 を占めた。

## 決定

### 1. 13番目の種別は「why の細分化」として足す

当初案は「文書から復元できる why」を新種別として足すことだったが、それは `doc-references` の
修復で足りる。足すべきは別の場所 — `why` が抱えている**未文書化の設計決定**である。

種別は 12 → 13 になる。ADR 0014 が要求する「版と ADR を要する」経路を踏む(ADR 0022 と同じ)。
0014 を上書きはしない — 閉じているのは利用者が設定で足せないことであって、項目数ではない。

`skills/pp/SKILL.md` の「a note that seems to need a **thirteenth** kind」は fourteenth になる。
ADR 0026 の 4/4/4 は 4/5/4 になる。

### 2. `doc-references` → `doc-restatement` に改名し、定義を復元元に揃える

| | 現 | 新 |
| --- | --- | --- |
| 定義 | a pointer to an ADR or another document | このリポジトリの既存の文書が既に書いている記述 |

**改名する理由は、機能しなかった原因が名前の側にあるためである。**定義文だけを広げても、
`doc-references`(参照)という字面はこの先もポインタを引き寄せ、内容の重複を弾く。ADR 0014 が
`history` → `legacy` を却下したときに名指しした故障機構と同じものが、逆向きに働いている。

字面のポインタ(「ADR 0007 参照」)は新しい定義に含まれる。取りこぼしは無い。

ADR 0014 は改名を「警告なく無効化される」ことを理由に却下したが、その沈黙は 0014 自身が同じ版で
潰している(`hooks/periplus-activate.js:95`、未知のキーは `config.json ignored — unknown kind` を
出す)。種別キーの改名はもう静かではない。

### 3. `why` は残余として存続し、`undocumented-design` が前に立つ

`why` の名前・定義文・設定キーは据え置く。位置だけが変わり、**最後に読む残余**になる。

判定材料(セッション → 文書 → コード、ADR 0022)は「設計が決めていない」を積極的に言えないことが
ある。0022 はその不確定を `unspecified-choices` に落としていたが、それは推測を分類として記録する
ことだった。残余があれば推測せずに済む。

`unspecified-choices` は動かさない。0件の原因は隣の `why` が先に吸ったことで説明でき、その吸引は
`undocumented-design` が前に立つことで消える。名前を疑うのは、この版の後も0件が続いたときである。

### 4. 読む順序

区別は全て順序が担う。順序は `skills/pp/SKILL.md` の表の下の散文、一箇所に置く。

```
1. 消えると次の読み手がコードを壊せる       → external-facts / contracts / current-limits
2. 目の前のコードが既に示している           → tautology
3. 文書と行を名指しできる                   → doc-restatement
4. 設計が決めた理由で、どの文書も持っていない → undocumented-design
5. 設計が決めていないと積極的に言える        → unspecified-choices
6. 4 とも 5 とも判定がつかない理由           → why
```

**1 が 3 より前であることは譲れない。**文書化済みの外部事実 — 例えば「.gitignore が改行で終わらない
と次の行を吸収する」 — が 3 に吸われると、ADR 0026 が数えた「地雷8件」がコードから消え、ADR 0004 が
防いだ「次の読み手が善意で壊す」が戻る。この規則は行き先の語彙を使わずに言える: **その記述が消えた
とき、次の読み手がコードを壊せるか。**壊せるなら主題はコードの外側の事実・契約・限界であり、それを
別に書いた文書があることは主題を変えない。

**2 が 3 より前であるのは、証拠が近いほうを採るためである。**コードが示しているなら、その記述は
文書が無くても冗長だった。加えて 2 の試験は無料で(コードは既に開いている)、3 の試験は検索を伴う。

**5 が 6 より前であるのは、5 が積極的な証拠を要求する試験だからである。**通らなければ自動的に 6 に
落ちる。逆順にすると残余が先に立ち、5 は永久に0件のままになる。

この順序により `why` は「まだどの文書にも書かれておらず、設計が決めたとも実装が決めたとも判定
できない理由」に絞られる。

### 5. `doc-restatement` の判定材料は永続記録に限る

**セッションは根拠にしない。**ADR 0022 が第一段にセッションを置いたのは「設計が決めたか」を
判定するためで、セッションは決定の発生源として有効だった。`doc-restatement` が問うのは「後から
読み返せる場所に既にあるか」であり、セッションは消える。口頭で言われただけの理由はどこにも
書かれていない理由であり、`undocumented-design` である。

**文書名と行番号を名指しできること**が「持っている」の条件。加えて、**名指しした行がその記述と
同じことを述べていること** — 違うことを述べているなら言い直しではない。文書が古い、あるいは
間違っている場合はこれで弾かれ、記述は 4 か 6 に落ちて失われない。

引用は `/pp-classify` の報告行にのみ現れ、どこにも保存されない。行番号は文書内で動くが、保存
されないので安定性は問題にならない。行まで求める意味はそこにある — 文書名だけなら「たぶん ADR の
どこかにある」で通る。行を出せというのは、実際に見つけたことの証明を要求する装置である。

CSV の形式は変えない。引用列を足すと行が自分の出自を持つことになり、一つの形式を四つのファイルで
共有している現在の性質が崩れる。

### 6. 検索は候補行ごとに行う

`/pp-discuss` が冒頭で文書を棚卸しするのは(ADR 0020)、**行き先の文書を名指しで提案する**には
在庫を知っている必要があるからで、あれは目録の仕事である。ここで必要なのは「この主張がどこかに
書かれているか」の**検索**であり、目録を先に読んでも検索は減らない。28本の ADR を頭に入れてから
3行を分類するのは規律ではなく儀式である。

在庫が要る分はファイル名で足りる。`0028-subagents-get-the-discipline-not-the-parents-backlog.md`
のような名前が既に索引になっている。当たらなければ `undocumented-design` か `why` のまま残る。
これは誤って消すのではなく誤って残す方向の失敗である。

`/pp-classify` が `config.json` を読まない規則(ADR 0014)は変わらない。読むようになるのは文書だけ
である。

### 7. 既定値

| kind | 既定 |
| --- | --- |
| `doc-restatement` | `drop`(`doc-references` からの継続) |
| `undocumented-design` | `periplus` |

`doc-restatement` を `drop` に置ける理由は復元性そのものではなく、**危ない側が既に前の段で拾われて
いる**ことにある。「文書にはあるが、消すとコードが壊れる」記述は 1 で確定し、3 に到達する行はその
試験を通り抜けた行だけである。誤射しても報告行に文書名と行番号が出るので利用者はその場で反論でき、
通っても行は `all.csv` に残る。

ADR 0002 が作った可変性は不変である。動くのは既定値ではなく種別の集合のほうである。

### 8. install は欠けているキーを既定値で追記する

`.periplus/` は追跡外なので、手で配られた設定が現場にある。改名後、そこに `doc-references` が
書かれていると警告が出てそのキーは既定に落ちる。

**install は既存キーに触らず、`DEFAULT_CRITERIA` にあって `config.json` に無いキーを既定値で
追記する。**

これは意味論的に何も変えない操作である。キーが無い状態と、キーが既定値で書かれている状態は
`loadConfig` から見て同一だからである。したがって「設定ファイルを黙って書き換える」の危険 —
利用者が選んだ値が変わる — が構造的に起きない。旧キーには触らないので、`doc-references: code` と
設定していた人の意図を推測する必要も無く、警告がそのまま「これは効いていない、消せ」の通知になる。
必要なのは知らせることであって、勝手に直すことではない(ADR 0014)。

**改名専用の仕掛けではない。**ADR 0022 で `unspecified-choices` が増えたとき、既に存在した
`config.json` はそのキーを永久に持たなかった。同じ穴が塞がる。

`skills/pp/SKILL.md` の "never overwritten after that" は「追記はする、既存の値は書き換えない」に
改める。設定ファイルがバイト単位で不変であることを固定しているテストも書き直す。

警告文も直す。現在の `config.json ignored — unknown kind "..."` は設定ファイル全体が無視されたと
読めるが、実際に落ちるのはそのキー一つだけである。この経路は今までほぼ発火しなかったが、今回の
改名が初めてこれを多数の利用者に見せる。

ADR 0026 が `why` を periplus に倒したとき追随しなかった二箇所(`pp-discuss` の「Three kinds」と
`CONTEXT.md` の「三つで」)を、この版で五つに直した。

## 影響

`/pp-refactor` にはセッションが無いため、5 の積極的証拠がほとんど揃わず、既存コードの理由は
`why` に落ちる。ADR 0022 は「誤検出は出るが、既存コードの未決着な設計判断を掘り出せることのほうを
採る」と書いており、**その掘り出しは弱まる。**失うのは分類の解像度だけで、行き先は 4・5・6 とも
periplus のまま変わらず、`/pp-discuss` には同じ行が同じ順で並ぶ。0022 が受け入れた誤検出を、
代わりに「判定できなかった」と正直に記録する形になる。この後始末は v0.6.1 で行う。

**表だけを読むと 4・5・6 は見分けがつかない。**区別は全て順序が担い、順序は散文一箇所にある。
今回の設計で最も脆い一点である。次にこの三つの分布が崩れたとき、最初に疑うのはこの一箇所である。
