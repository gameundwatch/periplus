# v0.7.7 — phase 1 は hook のものにする

`/pp` の第一段は、セッション開始時に既に文脈へ入っている本文をもう一度読む。読み終えても
`pre.csv` の行は増えない。**その時点で捕捉は終わっているからである。**再実行されているのは
規則の読み込みだけで、phase 1 そのものは一度しか走っていない。

原因は phase と実行者の対応にある。

| | phase 1 | phase 2 |
| --- | --- | --- |
| 何をする | 書きながら退避する | 分類して届ける |
| 規則の在処 | `pp-capture` | `pp-classify` + `pp-resolve` |
| **規則を文脈へ入れるのは** | **hook**(常時) | **`/pp`**(1 度) |

ADR 0033 は 2 行目の並びをそのまま実行順にした。3 行目を見ていない。**phase 1 の規則を文脈へ
入れる役は hook が持っており、`/pp` は持っていない。**規律の全体を覆うことと、状態を手続きの
列に混ぜることは別である。

## 決めたこと

**A. `/pp` は phase 2 だけを走らせる。** `/pp-classify` → `/pp-resolve` の二段になり、phase 1
は hook が撃っていると述べるだけにする。ADR 0033 の表題「三つ全部を通す」はここで偽になる。

覆う範囲は変わらない。変わるのは、覆うことを**本文の読み直しで果たさない**ことである。

**B. 捕捉規則は skill を降りる。** `skills/pp-capture/SKILL.md` を `hooks/capture.md` にし、
frontmatter を落とす。読み手は hook だけになる。

ADR 0032 は「`CAPTURE.md` を `skills/` の外に置く」を一度却下している。理由は「`/pp` から見て
phase 1 がどこにあるかが遠くなる」であり、**A で `/pp` が phase 1 を持たなくなれば消える。**
0032 の表題「手順はそれを走らせるコマンドに置く」に従えば、phase 1 を走らせているのは hook で
ある。

**C. hook が死んでいる場合の経路を諦める。** ADR 0033 が `/pp` に持たせた「hook が効いていない
とき `/pp` を呼べば捕捉規則が入る」を落とす。

0033 自身がその穴を「実際の穴は狭い」と書いている。`SessionStart(startup|resume|clear|compact)`
と `SubagentStart` で撃つので、残るのは node が無い・タイムアウト・hook 無効の三つだけである。
そのうえ効くのは**まだコードを書いていない**場合に限られる。書いた後に捕捉規則が届いても窓は
閉じており、そこでの復旧は `/pp-refactor` — ソースに入ったコメントを `pre.csv` に切り出す — で
ある。狭い一点のために `/pp` のたびに本文一つぶんを払っていた。

- `README.md:52-57` — `/pp` の説明と `/pp-capture` の項
- `README.md:74` — 元本の在処
- `docs/adr/0036` — A から C の理由。ADR 0033 を supersede する

- `hooks/periplus-activate.test.js` — `/pp` が名指しする段を見るテストを足す(D)

`CAPTURE_PATH` を読む 3 本は定数の変更に追随し、`TEMPLATE_FILES` に `pp-capture` は入っていない。

**D は当初この版で触らないものに挙げていた。**`/pp` が何段を名指ししているかを見るテストが無い
ことは ADR 0033 が穴だと書いたまま残っており、二段にする版でそれを繰り返す理由が無かった。番号
付きの行が `/pp-classify` と `/pp-resolve` の二つと一致することを見る。

## この版で触らないもの

**注入の量そのもの。** 1,834 字は動かさない。薄くする案は下の試験で +7.1% になった。問題は注入
側ではなく呼び出し側だった。

**`disable-model-invocation`。** B で `pp-capture` が skill でなくなるので、論点ごと消える。
ADR 0033 と 0034 がこの旗を巡って書いた検討は、掛かる先を失う。

**行形式が 5 箇所にあること**(`capture` / `pp-classify` / `pp-resolve` / `pp-refactor` /
`README`)。捕獲の規則であって呼び出しの話ではないので、別に積む。

## 注入を薄くする案の試験(記録)

この版で採らないが、作業場は scratchpad でセッションを跨いで残らないため、ここが記録である。

注入 2 変異 × AOJ の課題 2 問。副エージェントに注入文を前置きし、同じ課題を解かせた。

- A = 現行の注入 1,834 字
- B = ポインタ 308 字(規則はファイルを読めとだけ書く)

| | A | B |
| --- | --- | --- |
| AOJ 0015 / Ruby | 捕獲 3 — code 1 / drop 2 | 捕獲 3 — code 1 / periplus 1 / drop 1 |
| | 32,239 tok / 92 秒 | 33,696 tok / 97 秒 |
| AOJ 0021 / Python | 捕獲 3 — code 0 / periplus 2 / drop 1 | 捕獲 5 — code 1 / periplus 1 / drop 3 |
| | 30,164 tok / 78 秒 | 33,530 tok / 111 秒 |

4 回とも解答はサンプルと一致し、`pre.csv` は空、行形式も報告の文言も規則どおりだった。発火しな
かった回はゼロ。トークンは 4 回とも B のほうが多く、合計 +7.1%。注入で節約した 1,526 字より、
ファイルを読む往復のほうが高い。

n=2 で差が出ないことはどちらの証拠にもならず、副エージェントが `/pp` skill を使える状態だった
ため「ポインタを読んで従った」のか「skill が使えたから従った」のかも分離できていない。**この版
はこの軸を捨てるので、設計の穴は残したまま記録だけ残す。**
