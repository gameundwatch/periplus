# v0.5.0 — 分割を厳格にし、行き先を config.json に移す

## 概要

periplus を実運用しているリポジトリ(kagupon)の `all.csv` 108行を読んだ。**25行(23%)が
2文以上のまま classify を通過している。** そのうち割るべきでなかったのは3行だけで、残り22行は
kind が2つ以上混ざったまま1行に収まっていた。

混在の内訳は3つの型に分かれる。

| 型 | 件数 | 何が起きているか |
| --- | --- | --- |
| A. 相乗り | 14 | 「コードが何をするか。＋理由/外界の事実」。強いほうの kind が付き、tautology の半分が code に着弾する |
| B. history 巻き添え | 3 | history と事実が束。丸ごと `history` に落ちて drop され、事実が消える |
| C. 同一 kind 2件 | 5 | 別々の why が1行。現行規則(kind が2つ名付けられたら割る)では原理的に検出できない |
| D. 因果が文をまたぐ | 3 | 割るべきでない。正常 |

**型Aの原因は主語の欠落である。** 27行(25%)が主語を持たない節で終わっており、主語の無い断片は
自分の kind を主張できないので隣の kind を借りる。

```
#8 [external-facts] 「update_all はモデルを更新しないので a.floor_layer_index は古い。割り当てた値をそのまま返す」
                     └ 主語あり = external-facts ──────────────┘ └ 主語なし ────────┘
```

第2節に主語を補うと `このアクションは割り当てた値をそのまま返す` — コードが言っていること、つまり
tautology である。主語が無いまま隣にいたので external-facts の kind を借りて code に着弾した。

もう一つの欠陥は行き先の所在である。`skills/pp-classify/SKILL.md:32` は分類時に行き先を見るなと
命じているのに、`skills/pp/SKILL.md` の kind 説明そのものが行き先を根拠に判別を語っている。行き先は
`config.json` で変更できるので、**その根拠は設定次第で嘘になる。**これは今回の変更以前から存在する
矛盾である。

## 決定

### 1. 分割は推定有罪に反転する

現行は推定無罪である。

```
For each empty row, try to name its kind. If two names fit, the row is two rows.
```

2つ名付けられて初めて割る。この形は「これは因果だから1件」という自己弁護を許し、型Cの5件は
そもそも2つ名付けようがない(同一 kind が2つ)ので検出されない。

**hard stop を「1行1kind」に置いたまま、立証責任を割らない側に移す。**接続点があれば割る。割らないの
であれば理由を述べる。判定の主語は kind の数ではなく、行が何個の主張を含むかである。

### 2. すべての行が主語を持つ。補完は classify が行う

主節・従属節を問わず、主語の無い節を作らない。`/pp-classify` は各行に主語を補い、補った結果として
kind を名付ける。

**これは分割規則ではなく kind 誤判定の検出器である。**主語を補った瞬間にその行が何について語って
いるかが確定し、tautology が tautology として露出する。型A(14件)はこれで崩れる。

補完を classify に置くのは、規則の置き場を1箇所にするためである。capture 側に文体規則を足すと
ADR 0007(注入は capture rule だけ)と ADR 0013(捕獲が守るのは粒度だけ)の線を越え、コードから奪う
注意が増える。切った断面の主語欠落は分割の産物なので、切った側が補うのが素直でもある。

**`skills/pp-classify/SKILL.md:55-56` の `Splitting is a cut, not a rewrite` に例外を書く。**元の文が
主語を省略できたのは隣の節と主語を共有していたからで、切れば各片は自分の主語を要る。補完は復元で
あって書き直しではない。ただしこのコーパスには捕獲時点から主語の無い行(`#54「Illustrator と同じ挙動」`)
も含まれ、そちらを補うのは純粋な加筆になる。両方を classify の仕事として認める。

### 3. 断定系は強制しない。体言止めは block-headings の必要条件にする

当初は「文は断定系で終わること」を規則に足す案があった。**コーパスで検証して落とした** —
`しておく / と思われる / かもしれない / はずだ / だろう` は108行中0件で、この規則は何も変えない。

一方、**体言止めは検出器として機能する。**述語を持たない行は文ではなくラベルであり、コーパスで
体言止めの行はすべて `tautology` か `why` に落ちていた。

```
#17「同一パス /operator/templates/reorder の GET/PATCH 対」        [tautology]
#22「並び替えモーダル用の全件取得」                                 [tautology]
#34「並び替え保存後に一覧を読み直すためのトリガ」                   [tautology]
```

`/pp-classify` の判定はこうなる。

```
各行に主語を補う
  ├ 補えた(述語がある)  → 通常の kind 判定へ
  └ 補えない(体言止め)   → block-headings
```

**根拠は「ラベルは文ではない」だけである。**行き先を根拠にしてはならない(決定5)。

### 4. 因果免除は維持する

ADR 0013 の「因果(〜のため)は一件のまま」を変えない。因果を割ると原因と結果が別行になり、`why` と
いう kind が構造的に存在できなくなる。

```
「タイムアウトが多発したため非同期にした」
  → 「タイムアウトが多発した」  [external-facts]
  → 「非同期にした」            [tautology] → drop      ← why が蒸発する
```

型D の3行はすべて文をまたいだ因果であり、「1行1文」を規則にすればこの3行を壊す。**文の数ではなく
接続関係を見る。**従属節(〜ため / 〜ので)を作るものは1件、主節を並べるもの(逆接・並列・句点)は
2件である。決定2の主語補完もこの線に沿う — 従属節の主語を補うことと、従属節を切り離すことは別の
操作である。

### 5. kind の判別根拠から行き先を撤去する

`skills/pp-classify/SKILL.md:32-34` は既にこう命じている。

> **Ignore the destination column** — where a kind goes is `/pp-resolve`'s business, and
> knowing that `history` is dropped is exactly the pressure that makes a note get called
> something else so that it survives

ところが `skills/pp/SKILL.md` の kind 説明が、これに反して行き先で判別を語っている。2箇所ある。

```
:137-138  current-limits / upgrade-triggers
  「A limit ... belongs beside it; the intention to lift that limit ... belongs in the log」
  「Read the source alone ... Read the log alone ...」

:144-145  unspecified-choices の読み順
  「rather than something the source should carry」
  「What settles it is the design, which is why it goes to the log」
```

`why: drop` / `unspecified-choices: periplus` のような config では、この根拠がそのまま嘘になる。
**判別は「その note が何であるか」だけで語り、どこへ行くかを一切参照しない。**

`why` と `unspecified-choices` の読み順(external-facts → why → unspecified-choices)は残す。区別は
`/pp-discuss` での扱いが違うこと — why は設計の記述材料、unspecified-choices は設計の穴 — で説明する。

### 6. デフォルトの行き先を二つ動かす

**`why`: code → periplus。`block-headings`: drop → code。**

`why` は捕獲の41%(44/108)、code に届くものの61%を占める。44行を性質で仕分けた。

| 性質 | 件数 | 例 |
| --- | --- | --- |
| 地雷(触ると壊れる、コードから読めない) | 8 | `?? 0 を入れると…先に作られた床が選ばれる` |
| 実は external-facts(他所の振る舞い・外の事実) | 8 | `Illustrator と同じ挙動` |
| 設計書に既にある(D12/D17/D18 を指す) | 7 | `全件が1画面にあることが D12 のガードの前提` |
| コードから読める / 相乗り | 21 | `前後は鏡像なので配列を反転して使い回す` |

**ソースに残す価値が明確なのは地雷の8件だけである。**そして地雷も、決定1〜2 を通せば芯が
external-facts として抽出される。

```
#19「?? 0 を入れると欠損時に同値化して安定ソートで生成順に落ち、…問題が再発する」
  → 「安定ソートは同値のとき生成順を保つ」   [external-facts] → code
  → 「?? 0 は欠損値を同値化する」            [external-facts] → code
  → 「だから ?? 0 を入れない」               [why]            → periplus
```

**だから順序が制約になる。**分割の厳格化が先に入っていなければ、地雷ごと log に落ちる。

`block-headings` を code にするのは、ラベルが指すブロックが大きいときにラベルが働くためである。
ブロックの細分化が甘い可能性は残るが、コードを直すことは規律の仕事ではない(ADR 0021)。

結果、行き先は 4/4/4 に揃う。

```
code     : external-facts, contracts, current-limits, block-headings   ← 外側の何か
periplus : why, unspecified-choices, rejected-alternatives, upgrade-triggers  ← 未決の設計
drop     : tautology, doc-references, history, test-intent             ← 他所から復元できる
```

**「ソースに残るのはコードを読んでも分からない外側の事実だけ」という一行で説明できる形になる。**

kagupon の108行に当てた場合の着弾数。体言止めの block-headings への再分類は含まない。

```
                     捕獲   → code着弾(現行) → code着弾(新)
全体                  108        72 (67%)         28 (26%)
floorOrder.ts          22        13                5
index.tsx              17        14                3
useFloorReorder.ts     21        15                8
templates_controller    4         3                0
```

`floorOrder.ts` は50行前後のファイルに13件が着弾していた。2行に1コメントである。これが10行に1件に
なる。**1件ずつ見ればどれも妥当なのに束ねるとドキュメントになっている、という過剰は、行単位の
kind 判定では捕まらない。**行き先の移動でしか落ちない。

### 7. `config.json` が行き先の唯一の権威である

**SKILL 本文から行き先の記述を全撤去し、`.periplus/config.json` を参照させる。**

撤去は見た目ほど大きくない。`hooks/periplus-activate.js:7-20` の `DEFAULT_CRITERIA` は既に権威で
あり、`criteriaTable()` は SKILL.md の行き先列を JS の値で置換して出力している。

```js
128  return m ? `| \`${m[1]}\` |${m[2]}| **${criteria[m[1]] || m[3]}** |` : line;
                                              ↑ JS が勝つ    ↑ SKILL の列は到達不能
```

12 kind は両方に揃っているので `|| m[3]` は到達しない。**SKILL.md の行き先列は既に死んでいる。**

`skills/pp/SKILL.md:121-130` の code / periplus / drop の意味の説明は、**移設先を持たずに削除できる。**
`skills/pp-resolve/SKILL.md:47-65` に3つとも完全な形で書いてある。pp 本文にしかない内容は `drop` の
根拠(`recoverable from the code, from git log, or from an existing ADR`)だけで、これ自体がデフォルト
行き先を前提にした文章であり撤去対象である。

`skills/pp-classify/SKILL.md:30-34` の「行き先の列を無視せよ」は列そのものが無くなるので短くなる。
残すのは「config.json を読むな」の一文である。

`skills/pp-resolve/SKILL.md:29-32` のフォールバック(node が動かないとき SKILL.md の表を使う)は
行き先を **`config.json` を直接読む**に変える。決定8により config.json は常に存在し12 kind を完備
するので、JSON を読むだけで済む。SKILL.md より確実なフォールバックになる。

### 8. `config.json` は無ければ作り、消されたら復活させる

SessionStart ごとに存在を見て、無ければ12 kind 全部を書いたデフォルトで作る。**中身は一切上書き
しない。**

**`ensureWorkspace` に足してはならない。**

```js
41 function ensureWorkspace(root) {
42   const dir = path.join(root, '.periplus');
43   if (fs.existsSync(dir)) return;      // ← ここで即 return
```

`.periplus` が既にあれば何もせず返るので、同じ関数に足すと既存の利用者全員に永久に作られない。
ディレクトリと config.json は別々に存在を見る。

`ensureWorkspace` の設計思想(`:38-40` 「手で消した ignore 行は消えたまま」)とは違う振る舞いになる。
ignore 行は他人のファイル(`.gitignore`)への追記であり、config.json は periplus 自身のワークスペース
にある自分のファイルである。**規律が自分の設定ファイルを持つことと、他人のファイルを書き換えない
ことは別の話である。**

`criteria` イベントでは作らない。read-only な問い合わせが `.periplus/` を生やさない現行の設計
(`:255`)を維持する。

`DEFAULT_CRITERIA` は JS に残す。生成に要り、手で壊された config の穴埋めにも要る(`loadConfig` の
既存の振る舞い)。

### 9. `config.json` は追跡しない。作成も報告しない

`.periplus/` は全体が gitignore される(ADR 0009)。config.json が行き先の権威になっても、この線は
動かさない。`.gitignore` にも触らない。

新しいクローンにはデフォルトの config.json が生成され、チームが意図して書いたデフォルト設定と
見分けがつかなくなる。**これは運用するチームの問題であり、規律が引き受ける責務ではない。**生成した
ことをヘッダに報告する案も採らない。利用者の運用に対する通知は、規律の仕事ではない。

### 10. 語彙による免罪符検出は採らない

`念のため / 一応 / 万が一 / 安全のため / とりあえず / 後方互換 / 必要に応じて` を検出して drop に
送る案があった。**コーパスで0件。**

免罪符は字面に現れない。本来ドキュメントで吸収されるべき「やりすぎな説明」として、文章全体に
表出する。**行単位では検出できず、ファイルあたりの着弾密度にしか出ない**(決定6の `floorOrder.ts`)。
語彙リストは必ず漏れ、漏れた分だけ「リストに無いから通した」という別の免罪符を生む。

### 11. README は行き先を残す

`README.md:114-125` の4列表は行き先の列を持つ。**残す。**model が読んで分類に使う文書ではなく、
導入前の人間が読む紹介であり、デフォルトが何であるかは紹介に要る。`DEFAULT_CRITERIA` と二重に
なるが、ズレても分類は壊れない。

デフォルトが2つ動くので、その2行は更新する。

## 書き起こす ADR

**3本。**当初は6本、次いで4本の想定だった。分割の3決定(推定有罪・主語・体言止め)は一つの機構で
あり、片方だけ読むと根拠が欠けるため1本にまとめる — v0.4.0 が ADR 0024 を分割しなかったのと同じ
理由である。決定5(判別根拠から行き先を撤去)は独立させない。**新しい決定ではなく三箇所の食い違い
の是正**であり、是正の根拠は決定7の側にしか無い(v0.3.5 が引き金規則の揃え直しを ADR にしなかった
のと同じ扱い)。

| | |
| --- | --- |
| `0025` | 分割は推定有罪とし、すべての行が主語を持つ (決定1・2・3・4。ADR 0013 を継ぐ) |
| `0026` | ソースに残るのはコードを読んでも分からない外側の事実だけ (決定6・10。**ADR 0002 の既定を反転する**) |
| `0027` | config.json が行き先の唯一の権威であり、無ければ作られる (決定5・7・8・9・11。**ADR 0010 を覆す**) |

決定10(語彙リストは採らない)は 0026 の Considered Options に入る。却下の根拠が決定6の着弾密度の
議論そのもので、他の ADR では意味を成さない。決定11(README は行き先を残す)は 0027 の例外として
0027 に入る。例外が立っているのは「権威は config.json だけ」に対してであって、既定値に対してでは
ない。

**書き起こし済み。**3本とも `docs/adr/` にある。以下の実装はこの3本に従う。
