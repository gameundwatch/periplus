# `/pp-refactor` は既存コメントを複写せず、ソースから切り取る

`/pp-refactor` は収集の段階でソースを無傷のまま保ち、コメントを `.pre.md` に複写して
いた。理由も明記されていた — `/pp` の捕獲はまだ存在しないノートを扱うので失うものが
無いが、ここではコメントは実在し、フェーズの途中でセッションが切れれば一緒に消える。

この複写が `/pp` との非対称を生んでいた。`/pp` は空のソースに書き足すが、refactor は
既にあるコメントを消す・縮める・残すという別の操作をしており、三つの行き先すべてで
配送の中身が食い違う。v0.3.0 で phase 2 を `/pp-classify` と `/pp-resolve` に割った結果、
この非対称は「refactor 専用の配送手順」として残り続けることになった。

切り取りに変えると非対称が消える。収集を終えた時点でソースからコメントが消えている
ため、そのファイルは「`/pp` の phase 1 を終えたファイル」と区別がつかない。配送は
`/pp-resolve` をそのまま使えばよく、refactor 専用の手順は要らなくなった。

複写が守っていた安全は、ソースが変更済み・未コミットで残ることが引き受ける。`git diff`
が切り取った内容を持ち、`git restore` が戻す。作業ツリーが clean であることは要求しない
— AI ツール自身がバージョン管理を内部に持つため、規律の側で検査する必要がない。

## 帰結として同時に決めたこと

**抽出も分割の対象である。** ADR 0013 が縛るのは捕獲だけかという論点に、含むと答えた。
逐語で抽出して `/pp-classify` に割らせれば `.pre.md` の原子性は保たれないままになる。
逐語性を守る根拠として「`.pre.md` は removed の記録である」を挙げうるが、これは弱い —
収集中ソースは無傷であり、書き戻した後は `git diff` が何を消したかを正確に持ち、割った
行は同じ `file:line` と同じ作成日時を持つので兄弟であることは行から読める。

その代償として、`.pre.md` から元の一文を厳密に組み立て直すことはできない。接続詞が
落ちるためである。原状復帰はバージョン管理側の仕事になり、規律の側では書けない。

**ファイル単位の合意を廃止した。** 従来は差分を見せて合意を取ってから書き戻していた。
その合意は破壊の**前**にあったが、切り取りではその位置が存在しない。合意を破壊の後に
置けば「やったことへの事後承認」にしかならず、`/pp-list` と `/pp-discussion` を分けた
ときの理由(実行の前に反対できる場所を作る)を満たさない。掃除は対話を持たない一括処理
になり、最後に報告する。

これは「バッチは異議を素通しさせる」という従来の記述を覆している。覆した理由は上の
一点だけであり、`/pp-discussion` におけるファイル単位・エントリ単位の合意は変えていない。

**コメントの書き直しを許す。** 従来は「既に正しい形なら触らない」「全部そのまま残るのは
正常な結果」としていた。コメントのリファクタリングなのだから、書き直すのが仕事である。
ただし書き直しは翻訳ではない。言語規則は掃除にも効いたままで、これは v0.3.0 で
`/pp-resolve` に届いていなかったため、同じ版で明示した。

**コード本体には触らない。** `/pp-resolve` の「コメントを書く前にコードに言わせられない
か試せ」は掃除では走らせず、見つけたものは報告に一行出すだけにする。これは従来の禁止の
維持であって新しい決定ではないが、配送を `/pp-resolve` に委譲した以上、明示しなければ
自動的に破られる。

**この節の免除は ADR 0021 で不要になった。** 免除すべき手順そのものが `/pp-resolve` から
削除されたためである。「コード本体には触らない」という禁止は `/pp-refactor` の Boundaries に
残っている。

## Considered Options

- **複写のまま、refactor 専用の配送を持つ** — 破壊的にならない。ただし配送が三つの行き先
  すべてで `/pp-resolve` と食い違う手順を持ち続け、v0.3.0 の分割の利得が refactor には
  届かない。
- **範囲全体を先に切り取る** — 収集と配送が分離して見通しがよい。ただし合意の前に範囲
  全体が刈られ、`.pre.md` の `file:line` は切り取る前の座標を指したままソースは別の
  座標系になる。ファイル一つずつ完結させればどちらも起きない。
- **`/pp-resolve` から一律で編集権を外し、両コマンドで提案のみにする** — コード書き換えの
  衝突は消える。ただし `/pp` 側でこの手順が最も効く場面(コードが未固定でノートが新しい)
  を掃除の都合で潰すことになり、順序が逆になる。

## Consequences

`/pp-refactor` は破壊的なコマンドになった。ソースからコメントが消えるのは、行き先が
決まる前である。バージョン管理に載っていない場所で走らせれば、原状復帰の手段は無い。

skill の中身は薄くなった(範囲の確認と、ファイルごとの `cut → /pp`)。それでも独立した
コマンドとして残すのは、発火のトリガーが違い、既存コードを破壊するという危険も違う
ためである。
