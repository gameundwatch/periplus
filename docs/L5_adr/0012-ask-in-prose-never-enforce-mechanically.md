# 規律は文言で頼み、機構で強制しない

periplus の hook が決定的にやるのは4つだけである — `.periplus/` を作る、`.gitignore` に
一行足す、2つの件数を数える、規律の文面を注入する。いずれもモデルの遵守に依存せず書ける
処理で、ADR 0010 が言うとおり、そういう処理を確率的な指示に任せるのは筋が悪い。

その裏返しとして、**モデルの出力とツール呼び出しは検査しない**。捕捉が起きたか、完了報告
が述べられたか、コメントがソースに直接書かれなかったか — どれも hook からは判定できるよう
に見えて、実際には判定できない。ADR 0001 で ponytail の実装を確認したときに `PostToolUse`
によるコード検査が一切なかったのも同じ理由だと考えている。

## Considered Options

- **Stop hook で完了報告を検査する** — 却下。`periplus: N filtered` / `nothing captured`
  を述べたかどうかは最終応答を grep するしかなく、「言っていない」の判定は誤検出が多い。
  言い換え・部分的な言及・ユーザへの別の形での報告を全て取り逃す一方で、止められた側は
  何を直せばいいのか分からない。完了報告が実際に省かれるのを観測したら再検討する。
- **`PreToolUse` で Write/Edit の引数からコメント構文を検出する** — 却下。言語ごとの
  コメント構文の判定が必要で、文字列リテラル内の `//` や `#` と区別できず、誤検出のたびに
  正当な編集が止まる。ponytail が同じ機構を必要としていないのは、あちらの遵守が無料
  （書く内容が変わるだけ）で、periplus の遵守が追加の行動を要求するという非対称性による
  ものだが、その非対称性は文面の側で埋めるほうが安い。

## Consequences

不履行は差分に残らない。コメントを直接書いた場合は見えるが、そもそも何も捕捉しなかった
場合は何も残らず、空の `.pre.md` は正常な完了と区別できない。だから完了報告
（`skills/pp/SKILL.md` の phase 1 末尾）とステータスラインの件数が置かれている。どちらも
検査ではなく申告であり、規律が生きている証拠としては弱い。

この弱さは受け入れる。強制できる形にすると、誤検出でユーザの正当な作業が止まるコストを、
規律の発火率と引き換えに払うことになる。順序は文面が先で、文面で足りないと観測できた
ものだけが機構を得る。

文言で頼むということは、**文言が他の文言に負けうる**ということでもある。`/pp-refactor` の
`Stop when the scope is done or the user says stop` は、注入された完了ゲートを黙って
上書きしていた — 一般則より局所の許可が勝つためで、どちらも同じ散文なので競合は検出され
ない。スキルに終了条件や例外を作る一文を書くときは、その一文が常時注入されている規則の
どれを緩めるのかを確かめ、緩めないなら緩めないと書く。機構で強制しない選択の代償は、
規律の一貫性を散文のレビューで保たなければならないことにある。
