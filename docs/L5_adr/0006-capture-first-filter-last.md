# pre-comment は実装中に退避だけし、分類はコード完成後にまとめて行う

当初は「コメントを書きたくなった瞬間に分類し、行き先へ送る」形で実装していたが、
その瞬間にはまだコードが完成しておらず、判断の根拠が揃っていない。評価では
`0.2` というマジックナンバーの由来を説明するコメントが書かれたが、最終的に
`BASE_BACKOFF_SECONDS = 1 / PROVIDER_RATE_LIMIT_PER_ACCOUNT_PER_SECOND` と命名
されており、完成後に見れば不要だと即座に分かるものだった。書く瞬間には、その定数
はまだ存在していない。

そこで二段に分ける。実装中は判断せず `.periplus/pre.md` に退避するだけとし、コード
本体が完成した時点で一度だけ、完成物を目の前に置いて分類する。通過したものがソース
へ、periplus グレードのものが `.periplus/log.md` へ、残りはどこにも書かれない。

分類が実装の流れから外れることで、規律が実装中に要求するものは「コードに直接書かず
退避する」の一文になった。判断基準の表は完成後の一段でだけ引かれる。

## Consequences

「実装完了」は観測できるイベントではないため、フィルタを忘れると pre-comment は
退避されたまま残り、**ソースにコメントが一つも入らない**。これは本来避けたかった
「多すぎる」より悪い状態にあたる。対策として、pre.md が空になることを完了条件に
含め、SessionStart hook が未処理の pre-comment 数を報告する。

退避と分類が分かれたことで、規律の実行時点が二つになった。実装中に規律が効いている
ことは pre.md の増加として観測できるが、分類が正しく行われたかは完成後にしか分からない。

## 追記 (2026-08-19)

「完成した時点」の単位を [ADR 0038](0038-the-unit-of-completion-is-one-finished-change.md) が
定めた。単位は書き終えた一つの変更であって、タスクではない。上の二段 — 実装中は退避だけ、完成後に
分類 — の決定は動かない。
