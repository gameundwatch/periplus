# 「意図的逸脱」は判断基準の一項目ではなく、分解規則として扱う

`deliberate-deviation` は ponytail の `ponytail:` マーカーとの衝突を解消する過程で
判断基準の一項目として導入したが、他の項目と MECE ではなかった。

理由は二つある。一つは包含関係で、見直し条件を書くのは知って選んだ実装に対して
だけなので `upgrade-triggers` は常に意図的逸脱でもある。もう一つはより根本的で、
他の項目が「その記述は何についてか」を分類しているのに対し、`deliberate-deviation`
は「読み手はそれをどう受け取るべきか」を指しており、軸が異なる。軸の違うものを
同じ表に並べれば二重該当は構造的に避けられない。

評価でこれが実害として現れた。in-memory の辞書という「暫定であることの印(→ code)」
かつ「Redis へ移す条件(→ periplus)」である記述に対し、優先規則が無いためエージェント
は全体をログへ送り、ソースには印が一つも残らなかった。次の読み手が善意で「修正」する
という、この項目がまさに防ぐはずだった状況にあたる。

そこで項目としては削除した。

さらに評価のレビューで、同じ故障が別の箇所でも起きていることが分かった。Retry-After の
解釈について「秒形式しか扱わない」という現在の性質と「日付形式が来たら対応する」という
将来の作業が一つの記述に同居しており、記述全体が `upgrade-triggers` と label されたため
両方ともログへ送られた。ソースには意図の分からない迂回策だけが残った。

原因は項目の重複そのものではなく、その手前にある。**分類が節ごとではなく記述ごとに
行われていた。** 混在した記述は、大きいほうの半分に合う項目に丸ごと引きずられる。
そこで規律の順序を「分割してから分類する」に改め、分割線を次のように定めた。

- **今のコードについて真であること**（持っている制限、依存している条件、呼び出し側への
  義務、その形になった理由）→ code
- **後でやること**（見直す条件、却下した代替案、経緯）→ periplus

この言い方は `upgrade-triggers` と意図的逸脱の関係も説明する。「プロセスローカルである」
は今真であり、「Redis へ移す」は後の作業にあたる。「印」という語では、印に何を書くべきか
が定まらなかった。

## Considered Options

- **別軸のフラグにする** — どの記述も持ちうる属性として扱う。軸の分離としては正しいが、
  設定ファイルが二層構造になる。
- **優先規則を一行足す** — 両方該当時はコードが勝つ、と書くだけ。差分は最小だが、
  軸が混在している根本原因が残る。
- **削除して `why` に吸収させる** — `why` は既定で code なので印もコードに入る。ただし
  `why: periplus` に切り替えたリポジトリで印がコードから消え、事故が戻る。

## Consequences

判断基準は11項目から10項目になり、設定ファイルから `deliberate-deviation` が消える。
印をコードに残す義務は設定で無効化できなくなった — これは意図した硬直性であり、日誌が
gitignore される以上、ソースが次の読み手の唯一の手がかりになるためである。
