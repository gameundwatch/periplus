# `unspecified-choices` — 設計の空白を実装が埋めた選択

ADR 0021 が「コメントを書く前にコードに言わせられないか試す」一段を削ったことで、その一段が
拾っていた記述の行き場が問題になる。マジックナンバーの弁明である。

弁明は**設計者と実装者の食い違いから発生する**。設計が決めていない値や形を実装が裁量で決め、
その選択を後から正当化するために書かれる。これは今のコードについての事実ではなく、**未決着の
設計判断**である。行き先は periplus であり、`/pp-discuss` で方針を決める。

十二番目の種別として `unspecified-choices` を足す。

## 既存の種別との優先順位

弁明に見える記述は、`external-facts` と `why` の二つと重なりうる。順に読むことで分ける。

1. **外部の事実が値を決めているなら `external-facts`** → code。外部 API の制限は表の例そのもの
2. **設計が決めているなら `why`** → code
3. **どちらも決めていなければ `unspecified-choices`** → periplus

外部制約に導かれた選択は設計の空白を埋めていない。空白を埋めたのは外部の事実のほうである。
この順で読めば二重該当は起きず、ADR 0004 が警告した「軸の違うものを同じ表に並べる」ことにも
ならない — 三つとも「その記述は何についてか」を分類している。

## 判定材料の順序

「設計が決めていない」を何を見て判定するかを定める。**セッション → リポジトリの設計文書 →
コード**の順に、「これを決めているものがあるか」を見る。

第一段をセッションに置くのは、periplus が AI エージェントの現場で動く道具だからである。
設計者はユーザー、実装者はエージェントで、常に二者いる。「設計者と実装者が同一人物なら食い
違いは起きない」という反論はここでは効かない。`/pp` はコードを書いたのと同じセッションで
走るため、「この値はユーザーが指定したか、自分で決めたか」はその場で分かり、設計文書を要さ
ない。

`/pp-refactor` には掛けるべきセッションが無い。そこでは第二段以降からの推測になる。誤検出は
出るが、既存コードの未決着な設計判断を掘り出せることのほうを採る。定義は一つのまま、証拠の
強さだけが変わる。

## 掛けた後にログが膨らむことは受け入れる

掃除を走らせれば `unspecified-choices` がまとめて `.log.md` に入る。これは「このコードベース
には未決着の設計判断がこれだけある」という正しい信号であって雑音ではなく、減らすために
`/pp-discuss` がある。

v0.3.1 §7 が archive を `.all.md` と `.swept.md` に分けたのは、`.all.md` が**測定の器**であり
出自の混在が分布を読めなくするからだった。`.log.md` は**作業キュー**であるため同じ理由は
効かない。分離はしない。

## `/pp-discuss` は変更しない

弁明の主要な道は `docs` である。`/pp-discuss` で「コードを直す」と決まったなら、その内容は
設計変更であり、決定は `docs` に吸収される。コードを直すのはその決定の実行であって、periplus
が記録するものではない。五つ目の destination は要らない。

破壊的なコード変更が起きるとすれば、それは `/pp-discuss` でユーザーが一件ずつ合意した後で
あり、規律が自動で発火させるものではない。ADR 0021 が `/pp-resolve` から追い出したのはまさに
その自動発火である。

## Considered Options

- **「消しても次の読み手がコードを壊せない理由づけ」と定義する** — `/pp-discuss` が code 行きの
  判定に既に使っている試験の裏返しで、行とコードだけで判定でき設計文書を要さない。ただし
  `why` の相当部分がこちらに落ち、`why` → code の範囲が説明なく狭まる。
- **種別にせず分割規則にする**(ADR 0004 と同じ手) — ADR 0014 を破らずに済むが、割った後半を
  受ける種別が十一項目に無く、結局どこかに新項目が要る。
- **既存の種別で足りるとみなす** — 弁明の中身は `external-facts` か `why` に必ず落ちるとし、
  0005 の故障は行き先ではなく分量の問題だったと読む。ADR 0021 だけの小さい版になるが、
  未決着の設計判断がコードに事実として書き込まれる。

## Consequences

種別は十一から十二になり、periplus に着く既定の種別は二つから三つになった。

ADR 0014 は**上書きしない**。その Consequences は「種別を足したい状況は、設定では解決できず、
この ADR を上書きする議論として現れる。それが意図した硬直性である」と予告しており、この
決定はその経路そのものである。0014 が閉じたのは**利用者が設定で足せないこと**であって、項目数を
永久に十一に固定したわけではない。硬直性は働いた — 種別を足すのに版と ADR を要した。

`.log.md` に着く記述の性質が変わる。`rejected-alternatives` と `upgrade-triggers` は
どちらも「後でやること」だったが、`unspecified-choices` は「まだ決まっていないこと」である。
ログを「行き場を失った記述の一時置き場」とだけ読む現行の性格づけ(ADR 0003 の Consequences)は
これを抱えきれない。その書き直しは v0.3.6 で行う。
