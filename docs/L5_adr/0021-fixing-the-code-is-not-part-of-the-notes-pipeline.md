# コードを直す判断は記述のパイプラインに属さない

`/pp-resolve` は冒頭で「Where a kind goes is a lookup, not a judgement. The judgement was
made by `/pp-classify` when it named the kind, and it is not made again here.」と宣言して
いる。ところが同じファイルが、code 行きの全行に対して「コードに言わせられないか試せ」と
命じ、定数抽出・関数抽出・述語命名・アサーション追加を促していた(ADR 0005)。

これは記述の行き先についての判断ではなく、**コードの形についての判断**である。lookup だと
宣言した手順の中に judgement が一つ残っていた。

ADR 0004 と同じ形の問題にあたる。他の手順が「その記述をどこへ送るか」を決めているのに対し、
この一段は「そのコードをどう書くべきか」を決めており、軸が違う。軸の違うものを同じ手順に
並べれば、行き先の決定にコードの設計の決定が混入する。

そこでこの一段を削除する。

## 破壊性は根拠ではない

v0.3.1 §3 は同じ手順を `/pp-refactor` で止めており、根拠は「他人が書いた既存コードに当たる
から」だった。`/pp` が触るのは自分が今書いたばかりの未コミットのコードなので、この根拠は
そのままでは効かない。`/pp-resolve` には既に「A change to the code is still a change to the
code: show it before making it.」という合意ゲートもあった。

破壊は症状である。根拠は軸のほうにある。

## ADR 0005 の二つの帰結のうち、一つは残る

0005 は二つのことを決めていた。

1. コメントを書く前に、コードに言わせられないかを試す
2. コードに残る記述は事実の最短の陳述であって、コードの動作の説明ではない

**2 は残る。** `/pp-resolve` の code 分岐と `skills/pp/SKILL.md` の destination の説明が
そのまま持っており、0005 が防ごうとした「コードを散文で解説する」ことへの歯止めは消えない。
消えるのは 1 だけである。

## Considered Options

- **検出だけ残し、報告に一行出す** — v0.3.1 §3 が `/pp-refactor` に与えた形。破壊は消えるが
  judgement は `/pp-resolve` に残るため、根拠と半分矛盾する。
- **該当する行を periplus へ回す** — 「コードに言わせられるか」を誰かが判定しなければ行き先が
  決まらないので、judgement は消えず位置が移るだけになる。ADR 0014(行き先は種別の lookup)にも
  当たる。

## Consequences

定数化・関数抽出・述語命名は、規律としては誰の管轄でもなくなった。いずれも「コードの
読みやすさ」の問題であって「コードの外側の事実」の問題ではなく、periplus が保証するのは
後者だけである。実際 `API_RATE_LIMIT = 300` という名前は「その 300 が外部 API のレート制限
だ」という事実を半分しか運ばない。

コードを直す判断は、コードを書いている瞬間 — phase 1 — の仕事に戻る。

ただし 0005 が拾っていた記述のうち、捨ててはならないものがあった。設計が決めていない値や形を
実装が裁量で決めたときの理由づけである。これは ADR 0022 が種別として拾う。

`/pp-refactor` の「この手順を走らせるな」という免除も、免除すべき対象が消えたため削除した。
規律は一段短くなり、ADR 0005 の Consequences が予告していた「実行が重くなる」傾向はその分
戻る。
